### Holiday Inspiration App

<TagList items={["Streamlit", "Python", "APIs", "Web Scraping", "LLM Integration", "Live App"]} />

This project had the coolest outcome. It's a Streamlit app where a user can input a description of what they'd like from a holiday, to get suggested destinations with useful information such as weather, activities, and safety information.

<FigureImage
  src="/images/projects/rockborne/streamlit_demo.webp"

**In short:** it begins with a **context-stuffing** setup to have an LLM map a user description to a selection of three holiday destinations to choose from (out of a bespoke dataset of ~300 diverse locations). 
After destinations are chosen, the app loads weather/activities/safety via an IO layer backed by DuckDB. DuckDB is the source of truth: data is read from there first, and on a miss the IO layer fetches it (API or scraper), stores it, then returns it.

Here's a flowchart demonstrating how the application works at a high level:

<FigureImage
  src="/images/projects/rockborne/streamlit_flow.webp"
  alt="Holiday Inspiration App data flow diagram"
  caption="Holiday Inspiration App high-level diagram."
  width={3840}
  height={2160}
/>

For a real deployment I’d swap the in-container DuckDB file for a persistent database (e.g. Postgres) and add a TTL or scheduled refresh so cached API/scrape data doesn’t go stale. 
It works now because the cache starts empty after each cold start on Streamlit Community Cloud.
A natural next step would be upgrading from context-stuffing to a proper retrieval-augmented generation (RAG) setup, which I'd like to explore but wasn't within the scope of this project.
For more detail, take a look at the <a href="https://github.com/Jamie-Packer/streamlit-holiday-planner" target="_blank" rel="noopener noreferrer">GitHub repo</a>.

### Sports League Database

<TagList items={["SQL", "PostgreSQL", "Data Modelling", "Databases", "GDPR Compliance"]} />

Designed and implemented a local relational database for a fictional football league. It served as a good refresher on data modelling (I only had one module on this at uni; see <a href="/projects/university#database-theory--design">Database Theory & Design</a>).

<FigureImage
  src="/images/projects/rockborne/db_erd.svg"
  alt="Sports League Database ERD"
  caption="Entity relationship diagram for the database."
  width={3840}
  height={2160}
/>

The schema itself was standard 3NF OLTP stuff (the ERD covers it). What I found more interesting was learning about *where* integrity and compliance should live.

I included a mix of constraints and triggers into Postgres for data integrity, including some business logic rules (such as disallowing red carded players to later score in a match) that afterwards I learnt wouldn't live there in a production design (they'd be upstream).

I also added an audit log and a player anonymisation procedure. That was the bit that connected most clearly to how this kind of system would need to behave under GDPR: scrub PII on request, keep the keys so historical match stats still work, and retain a trail of what changed.

### Local ETL & Power BI Dashboard

<TagList items={["Python", "pandas", "ETL", "Power BI", "Data Visualisation", "Real Data"]} />

<ProjectLinks

This one was a two-parter: first a local Python ETL to build a dataset, then a Power BI dashboard using it. The topic was street-level crime data, enriched with population, deprivation, and economic data.

> **Fun Fact:** The most crime-ridden places in the south east are Brighton city centre and Gatwick airport.

**Part 1: the "ETL".** This was not production grade nor deployable (the [repo README](https://github.com/Jamie-Packer/uk-crime-etl) is honest about that). 
It was a training deliverable: raw files dropped into `data/raw/`, staged through `staging` → `interim` → `processed` / `reporting`, with helper modules in `src/` and a Jupyter notebook as the orchestrator - (that last part was a brief requirement, not a design preference). 

It has a clear grain (`lsoa_code × force × year_month × crime_category`), and a validation layer that gates each stage on failure.

The interesting engineering parts were designing the staged architecture and handling the messy joins underneath. 
For example police.uk flipped from different area codes mid-2023, population data lags the crime months, and missing coordinates get an `UNKNOWN` sentinel rather than being dropped so force-level totals stay honest. 

**Part 2: the dashboard.** Two pages framed for a time-poor, non-technical audience (force leadership / crime analysis leads), so the UX is deliberately app-like: metric toggles (volume vs crimes per 1k), bookmarks, info tooltips, and a global reset.

- **Overview:** point-in-time monitoring for a selected month: MoM / YoY KPIs, geographic hotspots, and force-level category mix.
- **Further Context:** deeper cuts over a custom date range: seasonality, category drill-down (14 police.uk types rolled into four macro groups), and scatter views linking crime rates to socioeconomic variables.

The dashboard side of this project was presented live.
